# 마켓플레이스 계획

에이전트 패키지를 서로 공유하고 사고팔기 위한 설계. 이 문서의 중심 질문은 하나다.
**무엇을 어떤 형태로 배포하는가.** 결제와 화면은 그 답 위에 얹힌다.

---

## 1. 지금 있는 것

코드에서 확인한 사실만 적는다.

| 것 | 현재 상태 | 근거 |
| --- | --- | --- |
| 패키지 | `relay.yaml`(BOM)을 가진 디렉토리 하나. 매니페스트 밖 파일은 기판에게 없는 것 | `relay.manifest.yaml` |
| 설치 | `installPkg`가 **디렉토리 절대경로를 장부에 적는다**. 복사하지 않는다 | `runner/installer.ts` |
| 장부 키 | `opts.name ?? path.basename(abs)` = 디렉토리 이름 | `runner/installer.ts` |
| 수정 레이어 | `~/.relay/drafts/<이름>/` (git 저장소) | `runner/draft.ts` |
| 발행 | 판정 → 커밋 → `v<버전>` 태그 → `~/.relay/releases/<이름>/<버전>/`에 **불변 스냅샷** 복사 → 장부 path 전환 | `publishDraft` |
| 롤백 | 장부 path 재전환 | `rollbackRelease` |
| 스냅샷 제외 | `.git`, `node_modules`, `.next`, `surfaces.view.out` | `COPY_SKIP`, `viewOutSkip` |
| 설치 시 실행 | 하네스 `info`/`setup` spawn, `conformHarness`가 동사 전수 실행, view `npm install` + `npm run build` | `installer.ts`, `conform.ts`, `build.ts` |
| 원격 | **없음.** 레지스트리도, 다운로드도, 계정도 없다 | 전 코드 |

핵심 관찰 하나. **배포 단위는 이미 만들어져 있다.** `publishDraft`가 굽는 릴리스 스냅샷이
정확히 "판정을 통과한, 빌드 산출물과 의존성이 빠진, 불변인 트리"다. 마켓플레이스가 새로
정의할 형식이 아니라, 이미 있는 것을 봉투에 넣어 옮기는 문제다.

## 2. 답: 배포 단위 = 릴리스 스냅샷 tarball

```
릴리스 스냅샷 트리  ->  tar + gzip  ->  <scope>-<name>-<version>.relay
                                       + sha256 다이제스트
```

- 내용물 = `publishDraft`가 `releases/<이름>/<버전>/`에 쓰는 것과 **완전히 같은 트리**.
  제외 규칙(`COPY_SKIP` + `viewOutSkip`)을 그대로 재사용한다.
- 다이제스트가 신원이다. 버전 문자열은 사람용 이름표이고, 무결성과 잠금은 sha256이 진다.
- 레지스트리는 업로드된 tarball 안의 `relay.yaml`을 **직접 파싱해서** 메타를 만든다.
  업로더가 보낸 메타를 믿지 않는다. 불일치는 발행 거부.

### 경로와 봉투는 다른 층이다

혼동하기 쉬운 지점이라 먼저 갈라 둔다.

- **경로**: 어디를 거쳐 옮기는가. 답은 웹이다. 웹 카탈로그에서 고르고 결제하고 설치한다.
- **봉투**: 무엇에 담아 옮기는가. 답이 tar + sha256이다. 사용자는 볼 일이 없다.
  npm을 쓰면서 tarball을 의식하지 않는 것과 같다.

실제로 어떤 느낌인가.

```
만드는 사람   relay publish orders --market
                판정 통과. @yuni/orders@1.2.0
                올림 12.4MB
                https://market.relay.dev/@yuni/orders

사는 사람     웹 카탈로그 -> 상세(권한 고지서) -> 결제 -> 설치 버튼
              또는 relay install @yuni/orders

기판          봉인 확인 -> releases/orders/1.2.0/ 에 전개 -> 장부 등재
              그 뒤로는 내가 만든 패키지와 구별이 없다
```

### 봉투 후보 비교

| 방식 | 되나 | 문제 |
| --- | --- | --- |
| tar.gz | 된다 | 없음 |
| zip | 된다 | **실행 권한 비트를 못 지킨다** |
| git clone | 된다 | 서버가 무겁고 유료 다운로드마다 인증 프록시가 붙는다 |
| OCI 아티팩트 | 된다 | 컨테이너 레지스트리를 하나 더 운영해야 한다 |
| 단일 파일 번들 | 안 된다 | 패키지 안에 node 프로젝트, 에셋, 셸 스크립트가 통째로 들어 있다 |

zip 탈락이 결정적이다. 하네스 어댑터 `run`이 전부 `rwxr-xr-x`인데(`packages/*/harness/*/run`)
zip은 실행 비트 보존이 플랫폼마다 다르다. 풀고 나면 `conformHarness`가 실행에 실패해 설치가
통째로 막힌다. tar는 mode 비트를 그대로 담는다. npm, pip, homebrew가 모두 같은 이유로 tar다.

sha256은 "받은 것이 올린 그것"이라는 확인 한 줄이다. 캐시를 믿을 근거이고, 잠금 파일의 의미이며,
유출된 버전을 특정하는 수단이다.

### 원격 설치는 로컬 발행과 같은 자리로 수렴한다

이게 이 설계의 요점이다.

```
로컬 저작:  draft  --publish-->  releases/<이름>/<버전>/  --> 장부 path
원격 설치:  .relay --verify-->  releases/<이름>/<버전>/  --> 장부 path
```

원격에서 받은 패키지도 똑같이 `releases/` 아래 불변 스냅샷으로 앉는다. 그래서
`relay releases`, `relay rollback`, 재발행 전환이 **원격 패키지에도 공짜로 동작한다**.
새 코드 경로가 아니라 기존 경로의 입구가 하나 늘어나는 것뿐이다.

### 왜 git 저장소가 아닌가

이전 세대(anpm)는 패키지당 bare repo를 Railway 볼륨에 두고 Git Smart HTTP + 인증 프록시로
배포했다(`relay-cli/git-server`). 작동은 했지만 비용이 컸다.

| 축 | tarball + 다이제스트 | 패키지당 git repo |
| --- | --- | --- |
| 무결성 | sha256 한 줄로 잠금 | commit sha를 따로 기록해야 같은 수준 |
| 유료 다운로드 | 오브젝트 스토리지 단기 서명 URL로 끝 | 요청마다 인증 프록시가 붙어야 함 |
| 운영 | 스토리지 + CDN. 상태 없음 | 영구 볼륨. "절대 지우면 안 되는" 자산 |
| 캐시 | 다이제스트 키로 CDN/로컬 캐시 자명 | 어려움 |
| 이력 | 릴리스 목록으로 충분 | 전체 이력이 딸려옴(장점이자 유출면) |

draft가 이미 git 저장소이므로 **저작 이력은 로컬에 남는다**. 레지스트리까지 git일 이유가 없다.
`github:user/repo` 형태의 소스 설치는 나중에 별도 입구로 추가하면 된다(이전 세대에 구현체 있음).

## 2.5 실물 조사: 지금 만들어진 패키지들

봉투 설계는 실물을 보고 정해야 한다. 체크아웃의 4개와 `~/.relay/releases`의 발행본 3개를
전부 열어 본 결과다.

| 패키지 | 크기 | 화면 | 하네스 | 에이전트 | 동사 | 데이터 거처 | 호스트 요구 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| @yuni/todo 0.1.1 | 216K | index.html | claude-code | 2 | 6 | `~/Relay/todo` | 없음 |
| @yuni/aside-pilot 0.1.0 | 272K | index.html | claude-code | 2 | 11 | `~/Relay/aside-pilot` | darwin + Aside.app |
| @yuni/video-studio 0.1.0 | 280K | index.html | claude-code | 2 | 12 | `~/Relay/video-studio` | ffmpeg, ffprobe, node, npx, whisper-cli |
| @relay/scribe 0.2.0 | 68K | index.html | 없음 | 없음 | 4 | `~/Relay/scribe` | 없음 |
| @local/music-sommelier | 52K | 없음(chat) | claude-code | 1 | 0 | 없음 | 없음 |
| @relay/system 0.1.0 | 800K (+485M) | Next.js 빌드 | 4종 | 2 | 16 | 저자 개인 경로 | git |

**성숙한 형태는 이미 수렴해 있다.** 발행된 3개가 같은 골격이다.
200~280KB, index.html 한 장짜리 화면, 어댑터 동봉, 앞단 에이전트가 일꾼에게 dispatch,
`scripts/` + `scripts/lib/`, 데이터는 `~/Relay/<이름>`. 매니페스트 주석까지 같은 이유를 적는다.
"설치본은 발행마다 새 스냅샷으로 바뀌므로 데이터는 그 밖의 홈 폴더에 앉혀야 한다."

즉 팔 물건은 **300KB짜리 tarball 하나**다. 무거운 것은 system 하나뿐이다.

### 그대로 싸면 안 되는 이유 여섯

**(1) 하네스 어댑터가 무게의 대부분이고 판본이 어긋난다**

todo 216KB 중 harness 156KB(72%). 그중 `icon.png` 하나가 122KB, 실제 로직 `run`은 22KB.
claude-code 어댑터가 세 판본으로 갈라져 있다.

```
15331B  packages/music-sommelier, packages/video-studio
22132B  릴리스 todo 0.1.1, 릴리스 aside-pilot 의 run-copy 잔여물
22747B  packages/system, 릴리스 aside-pilot, 릴리스 video-studio   (최신)
```

패키지 1000개가 각자 낡은 어댑터를 이고 다니면 어댑터 버그 하나에 1000번 재발행이다.
조치: 하네스 아이콘은 기판 제공으로 뺀다. 어댑터는 동봉하되 기판이 더 새 판본을 가지면
그쪽을 쓴다.

**(2) 선언 밖 파일이 그대로 실려 간다**

발행된 aside-pilot 안에 `harness/claude-code/run-copy`(구버전 어댑터 사본)가 들어 있다.
music-sommelier에는 `harness/run`, `harness/icon.svg`가 선언 없이 있다. `copyTree`가 트리
전체를 복사하기 때문이다.

마켓플레이스에서는 사고로 직결된다. 패키지 폴더에 둔 `.env`, 메모, 테스트 스크린샷이 그대로
배포된다. **매니페스트가 BOM이면 봉투도 BOM대로 싼다.** pack은 선언된 경로만 담고, 선언 밖
파일은 발행 때 목록으로 보여주고 뺀다.

**(3) 절대경로 오염**

`packages/system/relay.yaml`의 `dir: "~/somof/2608-02_opensource_UX개선/relay-oss/packages"`.
남의 컴퓨터에서 무의미하고 저자 폴더 구조가 공개된다. 발행 관문에서 `dir`은 `~/Relay/` 아래이거나
설치 시 사용자가 고르는 형태만 허용한다.

**(4) 패키지가 자기 디렉토리 밖에 의존한다**

`packages/system/surfaces/view/package.json`의 `"@relay/relayjs": "file:../../../../lib/relayjs"`.
릴리스 스냅샷(`~/.relay/releases/system/<버전>/`)에서는 `~/.relay/releases/lib/relayjs`로 풀려
존재하지 않는다. 장부에서 system만 체크아웃 경로에서 도는 이유로 보인다.

런타임 쪽은 답이 이미 있다. 데몬이 `/assets/chat-widget.js`를 `lib/relayjs/src`에서 서빙한다
(`runner/api.ts`). relayjs는 **기판이 제공하는 SDK**이지 패키지가 번들할 것이 아니다.
규칙: 패키지는 자기 디렉토리 밖을 참조할 수 없다. 발행 관문이 `file:` 의존과 상위 경로 참조를
거부한다.

**(5) 동사가 부르는 도구가 requires 에 없을 수 있다**

`packages/video-studio`(0.2.0)는 node/ffmpeg만 선언하는데 `scripts/transcribe.ts`가
`whisper-cli`를 부른다. 발행된 0.1.0에서는 손으로 고쳐 선언했다. 결제가 붙으면 이건 환불
사유다. 발행 관문에 정적 검사를 넣는다. 스크립트의 `execFile`/`spawn` 첫 인자를 긁으면
상당수 잡힌다.

**(6) 빌드 실패가 설치 실패가 아니다**

`buildView`는 결과만 돌려주고 던지지 않는다. 설치는 성공으로 끝나고 화면만 깨진다.
유료 판매에서는 빌드 실패가 설치 실패여야 한다.

### 상품 등급

| 등급 | 예 | 판정 | 무게 |
| --- | --- | --- | --- |
| 완제형 | todo, aside-pilot, video-studio, scribe | `surfaces.view` 있음 | 200~300KB |
| 대화형 | music-sommelier | `chat`만, `scripts` 없음 | 어댑터 빼면 4KB |
| 빌드형 | system | `surfaces.view.out` 있음 | MB급 + 설치 시 수 분 |

**1단계에서는 빌드형을 받지 않는다.** 설치에 npm install과 next build가 돌아 실패 지점이 많다.
발행된 3개가 전부 index.html 한 장인 것은 우연이 아니다. 빌드형은 레지스트리 CI 선빌드가
가능해지는 3단계에 연다.

## 3. 먼저 고쳐야 하는 것: 이름 충돌

지금 장부 키는 디렉토리 basename이다. 레지스트리에서 `@alice/orders`와 `@bob/orders`를
받으면 **둘 다 `orders`로 앉아 서로를 덮는다.** 마켓플레이스 이전에 반드시 닫아야 한다.

- 장부 레코드에 출처를 기록한다.

```ts
// runner/state.ts
export interface PkgRecord {
  path: string;
  origin?: {
    registry: string;        // https://market.relay.dev
    ref: string;             // "@alice/orders"
    version: string;         // "1.2.0"
    digest: string;          // "sha256:..."
    installedAt: string;
    purchase?: string;       // 유료면 구매 id
  };
  // ... 기존 필드
}
```

- 설치 이름 규칙: `@scope/name` -> `name`, 이미 있으면 `scope-name`, 그래도 겹치면 거부하고
  `--name`을 요구한다. 어떤 경우에도 `origin.ref`가 정본이다.
- `relay ls`가 `이름 / @scope/name@버전 / 출처`를 함께 보여준다.

부수 효과 하나. view 빌드는 `RELAY_BASE_PATH=/pkg/<설치이름>/view`를 굽는다. 설치 이름이
정해져야 빌드가 되므로, **레지스트리가 미리 구워 보내는 것은 설치 이름이 규범대로일 때만 가능하다.**
이건 3단계 최적화로 미룬다(10장).

## 4. 설치 관문: 매니페스트가 곧 권한 고지서

마켓플레이스 설치는 **모르는 사람의 코드를 내 컴퓨터에서 실행하는 일**이다. 지금 설치는
동의 없이 다음을 실행한다.

- `conformHarness`: 패키지가 동봉한 하네스 스크립트의 모든 동사를 실행
- `setup`: variant마다 한 번씩 실행
- `buildView`: `npm install` + `npm run build`

로컬 저작에서는 문제가 아니지만 마켓플레이스에서는 그대로 두면 안 된다.
다행히 매니페스트가 BOM이라 **권한 고지서를 기계로 계산할 수 있다.**

| 매니페스트 선언 | 사용자에게 보여줄 문장 |
| --- | --- |
| `services[].dir` | 이 폴더를 읽고 씁니다: `~/Documents/...` |
| `services[].url` | 이 주소로 나갑니다. 자격이 필요합니다 |
| `services[].source` | 컨테이너/프로세스를 띄웁니다 |
| `triggers` | 자동으로 깨어납니다: 매일 09:00 |
| `harness.variants` | 이 코딩 CLI를 당신 계정으로 돌립니다 |
| `edges` | 다른 패키지의 이 능력을 요구합니다 |
| `requires` | 이것들이 미리 깔려 있어야 합니다 |
| `hooks.deny` | 이 경로에는 닿지 않겠다고 선언했습니다 |
| workspace | 세션이 딛는 폴더 |

지켜야 할 불변식.

1. **`ring0`와 `workspace`는 매니페스트가 요구할 수 없다.** 지금도 CLI 플래그다. 그대로 둔다.
   레지스트리 설치는 절대 `--ring0`을 자동 부여하지 않는다.
2. **동의 전에는 패키지 코드를 한 줄도 실행하지 않는다.** 다운로드 -> 다이제스트 검증 ->
   매니페스트 판정(정적) -> 고지서 -> 동의 -> 그때 conform/setup/build.
   `installPkg`를 `prepare`(정적)와 `activate`(실행) 둘로 가른다.
3. 원격 설치는 `requires` 미충족 시 fail-loud 유지. 기판은 대신 설치하지 않는다.

## 5. 결제: 무엇을 파는가

정직하게 시작한다. **패키지는 소스를 동봉해 배송된다. 복제를 막을 수 없다.**
DRM을 흉내 내면 사용자만 불편하고 유출은 그대로 일어난다. 그래서 파는 대상을 다시 정의한다.

### 모델 A. 다운로드 권한 (기본)

구매 = 그 패키지의 아티팩트를 받을 권한 + 라이선스. 설치본은 계속 동작한다.
보호 수단은 법적 라이선스와 유출 추적(구매자별 다운로드 로그)뿐이다. 그걸로 충분한 시장이
있다(대부분의 템플릿/도구 판매가 이 모델이다).

### 모델 B. 무료 클라이언트 + 유료 원격 서비스 (강제 가능)

값이 나가는 로직을 `services[].url`(원격 MCP)에 두고, 패키지는 얇은 클라이언트로 배포한다.
결제하면 토큰을 발급해 vault에 앉힌다. **매니페스트가 이미 이걸 지원한다** (`auth.kind: token`,
`verify`, `help`). 복제해도 토큰 없이는 동작하지 않는다.

### 모델 C. 업데이트 구독

일회 구매 = 영구 사용 + N개월 업데이트 수신. 만료 후에도 설치본은 돌고, 새 버전만 못 받는다.
갱신 동기가 자연스럽고 강제도 쉽다(다운로드 시점 검사).

**권고: v1은 A + C를 기본으로 열고, B는 판매자 선택지로 문서화한다.** B는 기판 변경이 거의
없다(이미 되는 것). A/C가 레지스트리 쪽 일이다.

### 결제 스택

| 상황 | 선택 |
| --- | --- |
| 국내 위주, 정산 직접 | 토스페이먼츠 또는 Payple. 이전 세대에 `web/src/lib/payple.ts` 구현체 있음 |
| 해외 포함, 부가세/인보이스 대행 | Paddle (MoR) |
| 판매자 정산까지 위임 | Stripe Connect |

법적으로 챙길 것(한국): 통신판매중개업 신고, 디지털 콘텐츠 청약철회 제한 사전 고지
(다운로드 개시 시점), 판매자 정산과 원천징수, 표시광고. 1인 개발자 판매자가 붙는 순간
"중개"가 되므로 약관에 책임 분계를 명시한다.

## 6. 레지스트리 API 표면

기존 `/registry`는 **로컬 설치 장부**를 뜻한다(`runner/api.ts`). 이름이 겹치면 혼란이 크므로
원격은 `market`으로 부른다.

```
POST /v1/@scope/name/versions        발행. multipart(tarball) + 다이제스트
GET  /v1/@scope/name                 메타 + 버전 목록 + 가격 + 권한 고지서
GET  /v1/@scope/name/versions/x.y.z  단일 버전 메타(다이제스트, 크기, 게시 시각)
GET  /v1/@scope/name/-/x.y.z.relay   다운로드. 무료=공개, 유료=단기 서명 URL로 302
GET  /v1/search?q=&tag=              검색
POST /v1/purchases                   결제 개시
GET  /v1/entitlements                내 소유 목록
POST /v1/yank                        회수(설치 차단, 기존 설치는 유지)
```

발행 시 서버가 하는 판정: tarball 압축 해제 -> `relay.yaml` 파싱 -> 스키마 판정 ->
`name`이 인증된 scope 소유인지 -> 버전 불변성(같은 버전 재업로드 거부) -> 금지 패턴 검사
(경로 탈출, 심볼릭 링크, 크기 상한).

서명은 v1에서 하지 않는다. TLS + 다이제스트 + 레지스트리 계정으로 시작하고,
publisher ed25519 키 서명은 3단계에 넣는다. 지금 없는 것을 있다고 말하지 않는다.

## 7. CLI 동사

동사를 늘리지 않고 기존 것의 입구를 넓힌다.

```
relay install <디렉토리>            (지금 그대로)
relay install @scope/name[@범위]    새로 추가. 인자가 @로 시작하면 레지스트리
relay install ./x.relay             새로 추가. 아티팩트 파일 직접 설치
relay publish <이름>                (지금 그대로, 로컬 릴리스)
relay publish <이름> --market       새로 추가. 릴리스를 레지스트리로 밀어올림
relay pack <이름>                   새로 추가. .relay 아티팩트만 굽는다 (드라이런)
relay search <질의>                 새로 추가
relay market login                  새로 추가. 계정
relay update [이름]                 새로 추가. origin 있는 패키지 버전 갱신
```

`relay install @scope/name`이 하는 일 순서.

```
1  레지스트리에 버전 질의 (범위 해석)
2  유료면 entitlement 확인. 없으면 구매 URL 안내 후 중단
3  다운로드 -> ~/.relay/cache/<digest>.relay
4  sha256 검증. 불일치는 즉시 폐기
5  releases/<설치이름>/<버전>/ 에 전개
6  매니페스트 정적 판정 + requires 판정
7  권한 고지서 출력 -> 동의 (--yes 로 생략 가능, 비대화형은 필수)
8  conform + setup + view build
9  장부 등재 (origin 포함)
```

## 9. 운영 정책

노션 마켓플레이스를 대조군으로 삼아 정한다. 전제는 한 줄이다.

**노션은 문서를 팔고 우리는 실행 코드를 판다.**

노션 자신도 같은 회사 안에서 이 둘을 다르게 다룬다. 문서인 Templates 심사는 SLA도 피드백도
없지만, 코드가 도는 Connections는 5~10영업일 SLA와 피드백과 재제출을 공개 보장한다.
**우리는 전부 Connections다.** Templates 쪽 관행을 베끼면 안 된다.

### 9.1 환불과 청약철회 — 회수로 우회한다

"다운로드 개시 시점에 청약철회 제한을 고지한다"는 흔한 방식을 쓰지 않는다. 노션처럼
**회수 가능한 구조를 만들고 무조건 환불을 준다.** 회수가 되면 제한할 이유가 없어지고,
소비자보호 리스크와 구매 전환율이 동시에 풀린다.

다만 회수의 범위는 노션과 다르게 자른다.

| | 노션 | relay |
| --- | --- | --- |
| 상품 본체 | 삭제 | 삭제 (`~/.relay/releases/<이름>/<버전>/`) |
| 사용자가 만든 것 | **삭제** (편집분, 새로 만든 페이지까지) | **절대 건드리지 않음** (`~/Relay/<이름>/`) |

노션은 템플릿에 가한 편집까지 지운다. 우리가 그러면 재앙이다. 영상 편집기를 환불했다고
사용자의 영상 프로젝트 폴더를 지울 수는 없다. 다행히 구조가 이미 갈라져 있다.
코드는 릴리스 스냅샷에, 데이터는 홈 폴더에.

- **14일 무조건 셀프 환불.** 사유 불문
- 고지는 결제 직전 약관 동의 체크박스에 병기. 별도 제한 고지 화면을 만들지 않는다
- 남용 방지: 일정 기간 내 과다 환불 요청은 거절할 수 있다고 약관에 명시. 지역별 강행규정은 준수
- 환불액과 챠지백 수수료는 판매자 정산에서 차감

**한계를 정직하게 적는다.** 기판이 오픈소스라 회수를 거부하는 것은 쉽다. 그러나 노션도
환불 전에 내용을 복사해두면 그만이다. 회수는 정직한 다수에게 작동하는 장치이고, 그것으로
무조건 환불을 줄 근거는 충분하다.

### 9.2 라이선스 표시와 워터마크 — 경고는 산 사람에게 가지 않게

무단 재배포를 기술로 막을 수 없다는 것은 5장에서 정했다. 남은 것은 억제와 표시다.
전자책과 같은 처지이고, 전자책 업계가 간 길(DRM 에서 소셜 DRM, 즉 워터마크로)을 따른다.

**경고 문구를 설치 화면에 붙이는 흔한 방식은 쓰지 않는다.** DVD 앞의 FBI 경고와 같은
역설에 빠지기 때문이다. 그 화면은 돈을 낸 사람만 본다. 복제본을 받은 쪽은 아무것도 안 본다.

그래서 방향을 뒤집는다. **산 사람에게는 소유의 증거를, 복제본을 쓰는 사람에게는 사실 통지를.**

```
콘솔 카드 (산 사람)
  영상 제작소  v1.0.0
  yuni@musibe.com 님의 라이선스

설치 화면 (남의 사본)
  주의: 이 사본은 다른 사람에게 발급된 것입니다.
        발급 대상  y***@musibe.com
        발급 시각  2026-08-10
  계속 설치하시겠습니까? [y/N]
```

아래쪽이 **훔친 쪽이 보는 화면**이라 실제 억제력이 있고, 협박이 아니라 사실 진술이라
정직한 사용자를 불쾌하게 하지 않는다. 구현은 5장에서 정한 **공통 아티팩트 + 구매자별
서명 영수증**이 그대로 워터마크가 된다. 설치 때 영수증의 구매자와 현재 계정을 대조한다.
영수증을 지우면 그만이지만, 의식적인 행동 한 단계를 요구하는 것과 마찰이 0인 것은 다르다.

**문구의 자리를 층으로 나눈다.**

| 자리 | 무엇을 | 톤 |
| --- | --- | --- |
| 상세 페이지 | 라이선스 종류 (개인 1인 / 팀) | 상품 사양 |
| 체크아웃 체크박스 | 약관과 14일 환불 동의 | 한 줄 |
| 약관 본문 | 재배포 금지와 법적 책임 | 정확한 법률 문구 |
| 설치 화면 | 이 사본의 발급 대상 | 사실 진술 |
| 콘솔 카드 | 내 라이선스 표시 | 소유의 증거 |

상세 페이지에 **라이선스 종류를 상품 사양으로** 쓰는 것이 가장 실용적이다. "개인 1인
라이선스"가 적혀 있으면 팀이 쓸 때 팀 라이선스가 필요하다는 것이 자명해진다. 협박 없이
매출이 는다. 폰트와 스톡 이미지 업계가 이렇게 한다.

**지킬 것 둘.**

- **유료 패키지에만 적용한다.** 카탈로그 대부분은 무료일 것이다. 무료 패키지 설치마다
  저작권 문구가 뜨면 플랫폼 인상만 나빠진다
- **과장하지 않는다.** 한국 저작권법상 저작재산권 침해에 형사 책임이 따를 수 있고 영리와
  상습이면 고소 없이도 처벌 가능한 것으로 알려져 있으나, 조문과 형량을 화면에 적을 것이면
  변호사 검토를 받는다. "위반 시 즉시 고발합니다" 같은 문구는 사실이 아니면 그 자체로
  문제가 된다. "법적 책임을 질 수 있습니다" 정도의 사실 진술이 안전하고 효과도 다르지 않다

**문구보다 센 억제책이 이미 있다.** 복제본은 업데이트를 못 받고, 콘솔에서 한 번에 갱신되지
않고, 지원을 못 받고, 유출되면 누구 것인지 드러난다. 억제의 무게중심은 여기에 둔다.

### 9.3 심사 — 기계가 먼저, 사람은 고위험만

판매자 자격(계정 1회)과 리스팅 심사(건별)를 분리한다. 계정 레벨에서 사기와 자금세탁을
한 번 거르면 건별 심사가 가벼워진다.

노션 Templates의 "수개월 대기, SLA 없음"은 베끼지 않는다. 우리 초기 문제는 물량 폭주가
아니라 물량 부족이다. 판매자 승인이 수개월이면 아무도 오지 않는다.

**자동 판정이 노션보다 훨씬 강하게 가능하다.** 매니페스트가 BOM이기 때문이다.
2.5의 문제 여섯 개가 전부 기계로 잡히는 것들이었다.

```
경로 탈출, 상위 디렉토리 참조, file: 의존
dir 절대경로가 사용자 홈 밖을 가리키는가
동사가 부르는 바이너리가 requires 에 선언됐는가
선언된 디렉토리 안의 파일 목록 (잔여물 노출)
고위험 선언 유무 (triggers / edges / services.url / services.source)
이전 버전 대비 권한 증가
```

사람 심사는 **자동 판정을 통과한 것 중 고위험 선언이 있는 건에만** 붙인다. 노션이 인력으로
푼 것을 우리는 상당 부분 스키마로 푼다.

- SLA와 거절 사유를 공개한다
- 스캔할 권리는 확보하되 의무는 지지 않고, 거부하면 퇴출한다는 약관 문구를 둔다

### 9.4 회수(yank) — 딜리스팅과 긴급 회수를 나눈다

| 트리거 | 신규 설치 | 기존 설치 |
| --- | --- | --- |
| 판매자 자진 딜리스팅 | 차단 | 유지 |
| 환불 | 해당 구매자만 차단 | 그 구매자의 설치본 회수 |
| **악성 판정** | 차단 | **긴급 회수** |

노션은 딜리스팅과 회수를 분리하고 악성 템플릿이 남는 것을 감수했다. 문서라서 가능한 선택이다.
**우리는 그럴 수 없다.** 이미 설치된 악성 패키지는 새벽에 스스로 깨어나 사용자 폴더를 만질 수 있다.

현실적 최대치는 이렇다. 데몬이 주기적으로 설치된 패키지의 상태를 레지스트리에 조회하고,
회수된 버전이면 **즉시 비활성화하고 사용자에게 알린다.** 강제 삭제는 오픈소스라 못 하지만,
기본값이 정지인 것과 아무 일도 일어나지 않는 것은 다르다.

### 9.5 신고 — 웹과 로컬 콘솔 양쪽에

노션의 최대 구멍이다. 템플릿 상세페이지에도 크리에이터 프로필에도 신고 버튼이 없어서,
실제 표절 피해자가 비공개 커뮤니티에 공유된 링크로 신고 경로를 알아냈다.

- 웹 상세 페이지와 **로컬 콘솔의 설치된 패키지 카드 양쪽**에 신고를 둔다.
  설치해서 돌려본 뒤에야 이상을 아는 경우가 대부분이다
- 신고 폼이 증거 구조를 강제한다. 무엇이, 어느 버전에서, 어떻게 재현되는가.
  입증 책임은 신고자에게 있되 형식은 우리가 준다
- 판정이 애매한 영역(유사성 등)의 기준을 미리 공개한다. 안 그러면 매번 판정 불가로 흐른다
- DMCA 폼, counter-notice, 반복 침해자 정지는 표준대로

### 9.6 네임스페이스 — 이미 해결돼 있다

`relay.manifest.yaml`이 이름 형식을 강제한다.

```
pattern: '^@[a-z0-9-]+/[a-z0-9][a-z0-9-]{1,39}$'
```

스코프가 필수라, 노션이 겪은 선착순 플랫 네임스페이스 부채(사용자가 손으로 `-by-handle`을
붙이는)가 구조적으로 생기지 않는다.

남은 것은 둘이다. **scope 소유권 정책**(선점, 휴면 회수, 사칭 차단, `@relay` 같은 예약어)과
**로컬 장부 키 충돌**(3장). 후자는 0단계에 들어 있다.

### 9.7 수수료와 정산

- **정률만.** 정액 수수료를 붙이지 않는다. 노션의 `8% + $0.40`은 3달러짜리에서 실효 21%가
  된다. 우리 초기 카탈로그는 저가 위주일 것이 확실하다
- **MoR을 직접 떠안지 않는다.** 전 세계 VAT를 우리 규모에서 처리할 수 없다.
  Paddle 같은 MoR 위에 수수료를 얹거나, 국내만 먼저 열고 PG에 직접 정산한다
- 홀드 기간을 두고 격주 정산, 최소 지급액을 둔다
- **웹훅으로 실수령액을 쏜다.** 수수료와 세금을 뺀 금액, 환불 사유, 유입 경로까지.
  정산 불신은 API로 없애는 것이 가장 싸다

## 9.9 피벗 (2026-08-11): 퍼스트파티 스토어 우선

C2C(사용자끼리 사고팔기)를 뒤로 미루고 RelayOS 가 직접 올리는 스토어를 먼저 연다.
이유: 판매자가 0명인 시점에 판매자 인프라(계정, 자격, 심사, 정산, 관리자)를 먼저 짓는
순서는 relay-cli 세대가 밟았던 순서다. 계정 시스템 없이 신원 두 곳만 남긴다 —
**발행자 = 정본 저장소 push 권한, 구매자 = 라이선스 키(서버 장부의 토큰)**.

구현 계획은 [store-implementation-plan.md](store-implementation-plan.md), 구조 비교는
다이어그램 아티팩트 참조.

### C2C 호환 규율

나중에 일반 판매자를 붙이는 작업이 덧셈이 되도록 지금부터 지키는 여섯 가지.

1. **클라이언트는 계약만 안다.** 인덱스는 `version` 을 갖고, 데몬은 모르는 판을 명시
   에러로 거부한다. URL 은 설정값이다
2. **키 = 서버 장부의 불투명 토큰.** 오프라인 서명 라이선스 금지. C2C 전환 시
   "키를 계정에 귀속" 이 장부 한 칸 채우기가 되게
3. **유료 아티팩트는 첫날부터 비공개 버킷.** 공개 CDN 에 두고 URL 만 숨기지 않는다
4. **인덱스 엔트리에 seller 필드를 지금부터.** 값은 당분간 전부 퍼스트파티
5. **scope 규율 유지.** 퍼스트파티도 자기 scope 로만 발행, 일반명사 scope 선점 금지
6. **가격은 패키지 밖.** 리스팅(인덱스) 소유 (5장에서 기결정)

전환 시 실제로 갈리는 이음매는 둘뿐이다: 구매 증표 통합(키에서 계정으로 — 규율 2 가
덧셈으로 만든다)과 결제 슬라이스 교체(MoR 체크아웃에서 분할 정산으로 — 버리는 코드가
며칠치가 되게 작게 짓는다).

## 10. 단계

### 0단계 — 아티팩트 (레지스트리 없이)

산출물.

- `relay pack`: **매니페스트에 선언된 경로만** 담는다(2.5-2). 선언 밖 파일은 목록으로 보고하고 뺀다
- `.relay` 형식(tar+gzip)과 sha256 다이제스트
- `relay install ./x.relay`: 다이제스트 검증 -> releases 전개 -> 장부 등재
- `PkgRecord.origin`과 이름 충돌 규칙(3장)
- 이식성 관문: 상위 경로 참조와 `file:` 의존 거부(2.5-4), `dir` 절대경로 제한(2.5-3)
- 빌드 실패를 설치 실패로 승격(2.5-6)

검증: A 컴퓨터에서 pack -> B 컴퓨터에서 install -> 동작 -> `relay rollback`까지 정상.
대상은 발행본 3개(todo, aside-pilot, video-studio)로 한다. 이미 옳은 골격이라 기준선이 된다.
**이 단계만으로 이미 공유가 된다.** 파일을 주고받는 것으로 배포가 성립한다.

> **2026-08-10 완료.** pack/봉인/prepare·activate 분리/고지서/origin/로컬 선반 마켓 화면까지
> 구현·검증됨. 격리 홈에서 설치·업데이트·롤백·데이터 보존 왕복 통과.

### 0.5단계 — 퍼스트파티 무료 스토어 (9.9 피벗의 산출)

산출물: 정본 저장소(index.json + 아티팩트 + CI 판정), 러너의 원격 인덱스와 다운로드
캐시, `relay install @scope/name`, 정적 웹 카탈로그. 계정 없음, 서버 프로세스 0.

검증: 격리 홈에서 공식 인덱스만으로 5종 설치 왕복. 상세는 구현 계획서 5장.

### 1단계(구) — 레지스트리 MVP → **유료(키)로 재정의**

가격 붙은 엔트리, 결제(MoR 또는 토스) -> 키 발급 이메일 -> 콘솔 키 입력 -> redeem
함수가 비공개 버킷 서명 URL 반환. 키 장부가 첫 DB(표 하나). 14일 환불과 코드 회수(9.1),
라이선스 표시(9.2)가 이때 붙는다.

계정/scope 소유권/발행 API 등 기존 1단계 항목은 2단계로 이동.

### 1단계 — 레지스트리 MVP (무료만)

산출물: 계정과 scope 소유권 정책(9.6), 발행 API, 검색, `relay install @scope/name`,
권한 고지서와 동의 게이트(`prepare`/`activate` 분리), `@relay/market` view 초판,
발행 자동 판정 관문(9.3), 신고 동선(9.5).

검증: 남이 만든 패키지를 이름만으로 설치해서 실행.

### 2단계 — 결제

산출물: 가격 설정, 구매 흐름, entitlement, 단기 서명 다운로드 URL, 판매자 대시보드,
판매자 자격 심사(9.3), 14일 환불과 코드 회수(9.1), 긴급 회수 채널(9.4),
라이선스 표시와 영수증 워터마크(9.2), 업데이트 시 권한 diff 재동의,
정률 수수료와 정산 웹훅(9.7).

검증: 유료 패키지를 실제로 결제하고 설치. 미구매자는 다운로드 거부.
환불하면 코드는 사라지고 `~/Relay/<이름>` 데이터는 남는다.

### 3단계 — 신뢰와 규모

산출물: publisher 서명, 검증 배지, 레지스트리 CI 빌드로 view 선빌드,
`edges` 의존성 자동 해결(설치는 자동, 결재는 여전히 사람 손), 사람 심사 레인.
